# ROP v0.1 — Final Research Assessment

Status: Milestone 6 deliverable (2026-08-30). This assessment is based on the
implemented reference implementation, its tests (11 packages), the frozen v0.1
fixtures, the prior-art analysis (`docs/prior-art.md`), and the specification set
(`spec/`). ROP remains an experimental protocol / research project.

## 1. What ROP v0.1 actually standardizes

The interoperable **description** (Operation-level reversibility class, guarantee,
eligibility window), **recording** (immutable public Action Receipts; append-only
Action history), **evaluation** (per-Action current eligibility: server-time expiry
boundary, state, dependency constraints), and **verification** (provider-defined
postconditions with declared semantics classes and honest UNKNOWN outcomes) of the
reversibility of side-effecting operations — plus explicit representation of
uncertainty (`OUTCOME_UNKNOWN`) and residue. On HTTP: a discovery document, an Action
status resource, optional plan/reverse endpoints, and a stable RFC 9457 problem
vocabulary.

## 2. What remains provider-specific

What "reversed" means for a given business domain (semantic equivalence, §7); the
actual reversal mechanics (the provider's refund/delete/restore API); verification
postconditions and their strength; residue facts; dependency edges (they are
provider-declared safety facts); per-Operation postcondition catalogs (not yet on the
wire — see `spec/interoperability.md`).

## 3. Mechanisms reused from prior art

Compensation (Saga), idempotency keys, optimistic concurrency / CAS, outbox/intent
journals, WAL-style recovery discipline, reconciliation lookups, RFC 2119/9457/3339
normative machinery, `/.well-known` discovery. ROP claims novelty only in the
standardized representation and lifecycle across independent providers.

## 4. Interoperability value demonstrated

Within one implementation, end to end and tested: a machine client can discover
capability before execution, record Actions with receipts, evaluate per-Action
eligibility (including expiry to the nanosecond boundary), request reversal
idempotently, be told honestly `OUTCOME_UNKNOWN`, observe dependency-blocked reversals
refused rather than performed destructively, distinguish partial compensation with
residue from full reversal, and evaluate provider postconditions independently of
execution success. Core-only participation (no reversal invocation) is proven by the
capability-stripped test server.

## 5. Interoperability value that remains hypothetical

Cross-implementation interop: only one implementation exists, so the success
criterion (Master Prompt §88, "in principle") is untested against independent
adoption. Provider adoption is unproven — the invocation surface competes with every
provider's existing refund API. Reconciliation has no wire contract in v0.1, so
cross-organization resolution of unknown outcomes is unspecified. Per-operation
postcondition declaration is not yet machine-readable on the wire.

## 6. Features removed or deferred, and why

Deferred: batch reversal and cancellation (workflow territory, §29–30); reversal-of-
reversal; receipt signing (no key-management evidence; hook preserved — OQ-2); public
reconciliation (internal semantics proved sufficient for v0.1 — OQ-1); preflight
beyond OpenAPI (OQ-5); generalized residue taxonomy (free-form + lifecycle fields
held — OQ-3). Removed during research: recovery-by-re-execution (cannot distinguish
crash-before-call from crash-after-success; replaced by park-then-reconcile, M4).

## 7. Current security limitations

No authentication scheme is defined (403 semantics exist; principals are
deployment-defined); single-tenant mode is not a hardened multi-tenant claim; no
receipt signing or tamper-evident audit; a compromised provider adapter can misreport
both execution and verification; dependency edges are provider-declared and can DoS
reversal availability; problem `detail` echoes sanitized client input. The M6
second-pass review found and fixed one defect (unbounded detail reflection); see
`docs/security.md`.

## 8. Current distributed-systems limitations

Single-node SQLite (durability is local, not highly available); the missing-receipt
window (external effect before any durable record) is bounded by the intent journal,
never closed (§58); reconciliation is manual/administrative — no automatic scheduler;
idempotency protects ROP request handling, never provider exactly-once; throttling and
provider-availability semantics are deployment concerns, not modeled.

## 9. Current conformance model

Capability-based, two tiers. **ROP v0.1 Core** (required): discovery, Operation
metadata, receipts, eligibility, verification semantics, uncertainty representation,
problem types, evolution tolerance. **Optional advertised capabilities**: `planning`,
`reversal` (generic invocation), `reconciliation` (future). Dependencies and residue
are structural (representable everywhere, no switch). Claim language: "ROP v0.1 Core
+ `<capability>`". Vague claims ("ROP-compatible") are excluded. Full definition:
`docs/capability-model.md`.

## 10. Strongest argument FOR publishing v0.1

The reduced protocol is small enough to implement and audit in days, fills a real,
unfilled gap (no existing standard provides machine-readable per-Action reversibility
description/recording/eligibility/verification without workflow coordination —
verified against Saga/LRA/WS-BA), and is honest where its competitors were not:
unknown outcomes, residue, partial compensation, and dependency safety are
first-class, tested semantics rather than aspirations.

## 11. Strongest argument AGAINST publishing v0.1

The protocol's most novel surface — generic reversal invocation — is the one least
likely to be adopted (providers already own refund APIs), and the parts most likely
to be adopted (metadata + receipts) deliver value only when both sides implement
them, which no second implementation has yet done. Publishing now risks freezing a
surface whose reconciliation contract (the hardest problem) is deliberately absent.

## 12. Does the name still fit?

Mostly, with a caveat. "Reversible Operations Protocol" accurately describes the
core: it standardizes the *description and evaluation* of operation reversibility.
But it does not — and after this research, should not — promise the *execution* of
reversal (an optional capability) or any guarantee of success. If published, the name
should be qualified in the abstract: ROP standardizes the *accounting and semantics*
of reversibility, not the act, and not a guarantee. A rename is not required;
an honest subtitle is.

## 13. Recommendation

**PUBLISH_EXPERIMENTAL_V0_1** — as an experimental draft, explicitly labeled
non-normative for production. Work before any future v1.0 consideration separates
into two distinct categories:

### Required before any future v1.0 consideration

Concrete specification work identified in `spec/interoperability.md`:

- identifier-format constraints (charset/length/URL-path-safety for Action IDs);
- a wire representation for provider-defined per-Operation verification
  postconditions;
- a decision and registration strategy for the `/.well-known/rop` URI and the
  `ROP-*` header namespace (see OQ-10).

### Still-open research questions

Not automatically mandatory v1.0 features; they require evidence, not decisions
by fiat (see `docs/open-questions.md`):

- OQ-6 — whether retry guidance becomes protocol-visible;
- OQ-10 — the Well-Known URI / header namespace registration question itself
  (overlaps the strategy work above; the *research* question remains open even
  once the strategy work is scheduled).

Rationale: the implementation demonstrates internal coherence (specification audit,
22 frozen fixtures, five fuzz targets, adversarial tests mapped and passing); the
scope survived every opportunity to bloat (six milestones, each with explicit
non-goals); the research produced genuine negative findings (C3 demotion,
recovery-by-reconciliation) rather than feature accumulation; and the honest framing
— experimental, non-guaranteeing, provider-sovereign — is precisely what the field
is missing. Publication of an experimental draft is how the hypothetical value in
§5 gets tested.
